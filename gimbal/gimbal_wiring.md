## 一、接线表

排针上的位置（`motor_wiring.md` 里同一块排针的图）：

```
 pin 15  I2C4_SCL    ┃   UART_RX         pin 16   ← 我们不接
 ...
 pin 29  UART_TX     ┃   GND             pin 30   ← 共地
```

| 犀牛派 | 云台 | 线色 | 说明 |
|---|---|---|---|
| **pin 29**（UART_TX） | 云台 **RX** | — | 我们**只发**，所以只需要这一根信号线 |
| **pin 30**（GND） | 云台 **GND** | — | **必须共地**。不共地串口没有参考电平，收到的是噪声 |
| pin 16（UART_RX） | **不接** | — | 单向协议，我们从不接收。⚠️ 但也**别拿它当 GPIO**（见 `motor_wiring.md:161-162`） |
| pin 2/4（5V） | 云台 VCC？ | — | ⚠️ **先读第二节再决定** |

⚠️ `pin 29` 是 **TX**、`pin 16` 是 **RX** —— 这个方向在这次是**承重**的：接反了
云台永远收不到，而**回环测试照样通过**（短接是对称的）。见第四节的「它证明不了什么」。

## 二、⚠️ 电平：3.3V 驱动，**这次是有风险的**

排针是 **3.3V** 逻辑（`motor_wiring.md` 已记「3.3V逻辑忌接5V」）。这次的风险方向和
以前不同，值得写清楚：

* 我们的 **TX 输出 3.3V**，要去驱动云台侧的 **RX**。
* 若云台侧是 **5V CMOS** 输入，它的 `VIH` 通常是 `0.7 × VDD ≈ 3.5V` ⇒ **我们的 3.3V
  卡在阈值下面**。表现会是**时好时坏**：线短、干扰小时能识别，线长一点或有点噪声
  就开始丢帧 —— 而丢帧在本协议里是**没有帧头同步兜底**的（见 `gimbal_proto.py`），
  接收端的解析相位会永久错位。
* 若云台侧是 **3.3V 逻辑**（K230 这类 SoC 直接收），直连没问题。

**⇒ 接线前先确认云台侧 RX 的逻辑电平。** 是 5V 就加一个电平转换（或一个
最简单的分压/二极管方案），别赌「它应该能识别」。

⚠️ 反过来那一半是**安全的**：我们**不接**云台的 TX，所以不存在「5V 打进犀牛派
3.3V 引脚」这条路径。**不要把云台的 TX 接到 pin 16** —— 那才是真的会打坏板子。
（pin 16 之所以留着不接，除了「我们用不上」，也因为接了就要处理电平。）

## 三、节点名：**已上板实测定案 = `/dev/ttyHS1`**

2026-09-27 在板上实测（`ls -l` 是实测，不是厂商文档的转述）：

| 节点 | 属主 / 权限 | `aidlux` 能开? | 判断 |
|---|---|---|---|
| `/dev/ttyHS0` | `bluetooth:3002` `660` | 否 | **蓝牙**占着 |
| **`/dev/ttyHS1`** | `system:system` **`666`** | **能** | ← **PIN_29/PIN_16 那一对，我们要的** |
| `/dev/ttyHS2` | `bluetooth:bluetooth` `666` | 能 | **蓝牙** |
| `/dev/ttyHS3` | `root:root` **`600`** | **否** | 通用 40PIN 侧 PIN_11/13 |

**⇒ 不是靠「厂商文档说它是」定案的，是靠「真的把它开起来、配置读回通过」**：
`gimbal_proc` 在 `/dev/ttyHS1` 上 `open` 成功、`TIOCEXCL` 成功、`tcgetattr` 读回
`8N1 raw baud=115200` 与写下去的意图**逐位相符**。这一条已升为**高**证据等级。

### ⚠️ 一处**必须纠正的旧说法**：选错节点**会响亮失败**，不是静默

本文早先写的「选错的那个：`open` 成功、`write` 返回 6、日志全绿、云台一动不动」
**在本板不成立** —— 那个可怕形状的前提是错节点**也能被打开**，而实测 `ttyHS3` 是
`root:root 600`，`aidlux` 打不开它，会直接 `EACCES`（`gimbal_proc` 退出码 2，
`start_gimbal.sh` 预检先给退出码 7）。

**但这不等于可以放松**：① 若以 **root** 跑（或以后有人 `chmod` 宽了）那个静默形状
立刻回来；② **真正剩下的静默风险不在节点名，而在「节点对了、但排针没接对」** ——
见第四节：回环证明不了 PIN_29 是 TX 还是 RX。

### 定案命令（换板/换固件后复核用）

```bash
ls -l /dev/ttyHS*                     # 节点在不在、属主/权限
ls /sys/class/tty/ | grep -i hs       # 内核认得哪些 tty
cat /sys/class/tty/ttyHS1/dev         # major:minor
aidlux 在不在 dialout: id aidlux       # 实测:在(组 20)
有没有 getty 占着: systemctl list-units | grep -i ttyHS   # 实测:无
```

⚠️ **把「节点缺失」和「名字猜错」分开**：`ls /sys/class/tty/` 有而 `/dev/` 里没有
⇒ 是 udev 没建节点，靠上面的 `major:minor` 用 `mknod` 补，**别猜号**。

### 权限

标准是 `root:dialout 0660`，前提是你的用户在 `dialout` 组里：

```bash
id aidlux; getent group dialout
```

⚠️ **组权限的时序坑**：`gimbal_proc` 是 `setsid nohup` 起的，继承**启动它的那个
shell** 的补充组。把 aidlux 加进 `dialout` **不会影响已经跑起来的进程** ——
必须**重开会话**。

⚠️ **先看再决定。** 若第一次 `ls -l` 就正常，**不要**照抄一个 `fix-uart-perms.service`
出来 —— 那是给「确认会复发」的坏状态准备的。真要写，**必须复刻
`fix-gpio-perms.sh` 的判据**（以「复核实际属主/权限」为成功判据、坏状态退出码 1），
**绝不能**是「无条件打印已修正 N 个」那个已被否掉的写法。

## 四、回环测试：验节点 + 免费验 raw 配置

⚠️ **这一步至今没做过**，而定案优先级已被第五节抬高：它是目前**唯一**能证明
「`/dev/ttyHS1` 就是排针 PIN_29/PIN_16 那一对」的办法，而那个映射错了就**完全静默**
（本机日志一切正常，字节却从另一块排针出去了）。

```bash
bash ~/start_gimbal.sh stop          # ⚠️ 串口是 TIOCEXCL 独占的,必须先停主进程
# 用一根跳线**短接 PIN_29 ↔ PIN_16**
/usr/bin/python3 ~/gimbal_proc.py --loopback
# ⚠️⚠️ 测完**必须拔掉跳线**
```

⚠️⚠️ **短路的是 29↔16，不是 29↔30。** 接错就是把驱动器输出**直接对地**。

### 它能证明什么

* ✅ **这个节点就是 PIN_29/PIN_16 那一对** —— 排除了 `ttyHS3`（它的 TX/RX 在
  PIN_11/PIN_13）。
* ✅ **OPOST 关了** —— 载荷里刻意放了 `0x0A`，没关的话回来会变成 `0D 0A`（长度变了）。
* ✅ **IXON 关了** —— 载荷里放了 `0x13`/`0x11`，没关的话驱动会当场暂停输出、读回超时。
* ✅ 字节流**无缝**（发送的 N 字节原样读回 N 字节）。

### ⚠️ 它**证明不了**什么（这条界限必须守住）

* ❌ **证明不了 PIN_29 是 TX 而不是 RX** —— 短接是对称的，两种接法回环都通。
  对**只发**的应用这是致命的：若 TX 其实是 PIN_16，云台**永远收不到**，而回环
  照样通过。⇒ 必须做一次**外部观测**（见下）。
* ❌ **证明不了编码对不对** —— 回环用的 `encode_frame` 和被验的是同一个。
  编码只有 `gimbal_test.py` 从 C 源码抄下来的**黄金向量**能判。

### PIN_29 是 TX 的确认（唯一的做法）

接一个 USB-TTL 适配器，**只接 GND**，适配器的 **RX 接到 PIN_29**：

* ⚠️ **绝不接适配器的 TX** —— 那会把 5V/3.3V 打进排针。
* 用 `115200` 打开适配器，一边跑 `gimbal_inject.py`，一边看适配器收到的字节。
  收到形如 `AA .. .. .. .. ..` 的 6 字节组 ⇒ PIN_29 确实是 TX。

## 五、⚠️⚠️ 速度是**锁存**的 —— 所以「停发」= 失控

**已定案（收端协议原文，证据等级 高）**：`0xAA` 是**速度帧**，`steps/s = |value| * 80`，
而**收端没有任何超时保护** —— 协议原文：「发完 dx=100 不发新帧，云台会**一直转下去**」。

⇒ 三条推论，每一条都改过一个先前写反的结论：

| # | 推论 | 先前写的是什么 |
|---|---|---|
| 1 | **要停就必须显式发 `(0,0)`**，`(0,0)` 是**速度 0**，不是「角度回中」 | 早先把 `(0,0)` 叫「回中」，把「不发 `(0,0)`」当安全 |
| 2 | ⚠️ **断链时停发 = 云台按最后的速度一直转到撞限位** | 早先的 `HOLD(停发)` 设计，本意是「保持不动」，**结果正好相反**。2026-09-27 已改成「持续发零速帧」 |
| 3 | 定节拍连发**是协议要求的**（点 1），不是可选项 | 早先当成一个「等定案」的悬案 |

⚠️ **端口坏（`_break_port`）是唯一堵不上的洞**：那时我们**发不出零速帧**，
云台会一直转。本机日志会**响亮**说出来，但**软件救不了** —— 要人去断云台电源。

### 斜坡：同样是**必做项**，而且必须在我们这边做

协议点 2 原文：「**没有加减速斜坡。** 直接发 0 → 8000 是瞬间跳变，会**丢步/堵转**。
斜坡要在你这边做，比如每 20 ms 让值变化不超过 ±5。」

⇒ `gimbal_slew_per_s: 250.0`（= 5/0.02）。**关掉它（置 0）就是那个会堵转的形状。**
⚠️ 这不是「调响应速度」的参数，是**安全参数**。

### 判定/演示实验（**已不是**「绝对量还是增量」那个实验）

```bash
bash ~/start_gimbal.sh stop
/usr/bin/python3 ~/gimbal_proc.py --pulse 50 0 1        # 推上去 1s → 自动回零
```

⚠️ 这个模式发的是**原始协议值，不套 `invert`、不经 UDP** —— 它的全部意义就是看
`dx=+50` 到底让云台往哪边动。套上反转就永远判不出方向。
⚠️⚠️ **别改回「只发一帧」**（它早先叫 `--single-frame`）：速度锁存 ⇒ 发一帧就走
= 云台**一直转到撞限位**。现在它会**自己把速度降回零**再退出，这是承重的。

## 六、方向（`gimbal_invert_x` / `gimbal_invert_y`）怎么定

```bash
python3 ~/gimbal_inject.py --axis-sweep
```

**先只扫 dx（dy 恒 0），再只扫 dy（dx 恒 0）**，一次回答三个问题：

1. **方向** —— dx 从 −100 到 +100 时云台往哪边偏。想让它朝另一边就把
   `gimbal_invert_x` 置 `true`。
2. **行程** —— 哪几档顶住不动/嗡嗡响，那就是撞限位了，指令值域要收窄。
3. **两轴是否真的独立** —— 扫 dx 时云台**有没有同时上下动**。有的话说明协议里的
   dy 不是我们以为的那个轴，或者接收端在做混控。

⚠️ **`invert_x` 和 `invert_y` 是两个独立的未知量**，别拿一个去推另一个 ——
和 `motor_params.yaml` 的 `servo_invert` 同一性质（那份文件明写「**别照着名字猜**」）。

⚠️ **反转发生在 `gimbal_proc` 的接收侧**，不在前端、也不在 `gimbal_inject.py`。
只看注入器的日志会得出错误的方向结论，所以 `gimbal_inject.py` 会把「我注入的值」
和「进程真正发出去的值」**都**打出来。

## 七、⚠️ 供电：这次是**已知会低压**的那条轨

`motor_wiring.md` 记着：排针 5V（pin 2/4）正给 L298N 逻辑供电，**相机也在同一条轨上**，
而这条轨**没有任何文档给出电流预算**。

**云台若也从 pin 2/4 取 5V，就是给一条已知会低压的轨再加负载。** 而它的失败表现是
**先在相机/SLAM 上出现**（`motor_wiring.md:318` 已记这个对照）—— 排查方向会**完全
跑偏**：你会去查 SLAM 参数、查相机驱动，而真凶是云台在拉电流。

⚠️ **软件检测不到低压。** 别指望改参数能修。

**正解**：云台走**独立 5V BEC**（接电池，与犀牛派**共地** —— 共地不能省，串口要参考电平）。

| 云台抖/丢帧，日志正常 | ⚠️ **电平卡在阈值**（第二节） | 线缩短试试；或量云台侧 RX 的电平 |
| **相机/SLAM 先出问题** | 排针 5V 轨被云台拉低压了 | 断开云台电源看是否恢复。**软件检测不到** |
| 云台一直朝一个方向转、松杆也不停 | 零速帧没到（同上）；**不是**「增量语义」——那条已排除 | 第五节 |
| `EBUSY` 打不开串口 | 另一个进程占着（TIOCEXCL 独占） | `sudo fuser -v /dev/ttyHS*` |
| 日志刷 `termios 被改` | 有 `serial-getty` 在抢这个 tty | `systemctl list-units \| grep -i ttyHS` |

## 九、软件只能**证伪**，不能确认

## 附 1、「云台不动」的排除顺序（**硬件那条线，还没做**）

用户 2026-09-27 把硬件验证推迟了。到动手时**按这个顺序**做，别跳步 ——
前两步各只花一根线/一个转接板，而它们能把「软件」整段排除掉：

| 步 | 做什么 | 能证明什么 | **不能**证明什么 |
